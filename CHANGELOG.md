## [Unreleased]

Preparing the first public release.

### Changed

- The project is called **Kontor**. The binary is `kontor`, the Homebrew cask is
  `lx-wnk/tap/kontor`, the container image is `ghcr.io/lx-wnk/kontor`, the macOS
  bundle identifier is `com.lxwnk.kontor`, and the Go modules are
  `github.com/lx-wnk/kontor/{sdk,server,desktop}` with plugins under
  `github.com/lx-wnk/kontor-plugin-*`. The installer's environment variables are
  now `KONTOR_BIN_DIR` and `KONTOR_VERSION`.
- Configuration variables are now `KONTOR_*`. The old `DASHBOARD_*` names are
  still read, the new ones win when both are set, and the server warns once at
  boot when it found only old ones.
- A new installation writes `~/.claude/kontor-tasks.db`; one that already has
  `dashboard-tasks.db` keeps using it. The plugin encryption key is copied to
  `kontor-secret.key` on first boot and the previous file is kept as a backup.
- The hook script and its secret file keep their old names in this release. The
  copy already installed in `~/.claude` has those paths baked in, so renaming
  them without reinstalling the script would stop it authenticating.

### Changed
- **The sidebar stops moving the item you are aiming at.** Hovering the icon rail expanded it, and two things that render only in the expanded state changed the geometry underneath the pointer: the group captions (`MONITOR`, `BUILD`, `INSIGHTS`) inserted three rows, and the footer laid its three action buttons out in a row instead of a column, making it ~80px shorter. Because the last nav group is bottom-anchored with `mt-auto`, that second one lifted every Insights item by that much. Measured against the running app: `Workflows`, `Cost` and `Eval` moved 76px the moment the panel opened — nearly two rows — so a click begun over one of them landed on its neighbour. The caption now sits in a fixed-height box present in both states (the icon rail keeps its centred rule inside it), and the footer keeps one column layout throughout. After the fix those three rows sit at the same offsets in both states; the top five move 3px, from the title block that still appears only when expanded, which is well inside a 40px row. Both invariants have tests that fail against the old markup.
- **The Eval view draws its charts on the first paint, and stops rate-limiting itself on the way there.** Two defects on the same screen, both visible only in a running app. The nine metric cards sat blank because the draw was triggered by a watcher on `snapshots` alone, while the `<svg>` it draws into is gated by `isLoading` as well — the watcher fired while the element did not exist yet, `renderChart` found a null ref and returned, and nothing re-triggered it until the 60-second poll replaced `snapshots` again. The watcher now covers both gates. (The same line moved from `queueMicrotask` to `nextTick`, which is the primitive that actually orders after Vue's DOM patch; on its own it changed nothing measurable, and the test proves it — reverting only that stays green.) Separately, the view fetched one request per metric, so a single page load sent 21 API requests in one second against the server's own per-IP burst of 20 and answered itself `429 Failed to load eval data`. `/api/eval/metrics` returns every metric without a `metric` filter, so the client now makes one request and groups the rows itself: 13 requests per second instead of 21. The composable test that asserted "at least ten fetches" had written the fan-out down as a requirement; it now asserts one. `CostAnalyticsView` got the same `nextTick` for the same reason its own comment already gave, though its charts survived the old primitive because their cards use `v-show` and the refs exist from mount — no defect was observed there.
- **Mission control surfaces an agent's own question, not only a pipeline permission.** Its empty state promises that agents will interrupt there, but the centre ranked permission requests and plans waiting for approval and nothing else — so an agent holding an AskUserQuestion on its terminal left the centre reading "Nothing needs you" while the needs-you band showed the question one view away. `question` joins the ranking between `permission` and `plan`: a permission blocks a tool call already in flight, a question blocks the turn around it, a plan blocks nothing until a human looks. The centre renders the same `QuestionCard` and `ConfirmCard` the band renders rather than growing a second way to answer, and the review/submit screen that closes a multi-question flow counts too — leaving it out would have let the centre fall silent at the last step of the flow it had just surfaced. The POST both places send is now one function, `sendQuestionAnswer`. The centre's context line also stopped printing a trailing separator for items that carry no stage.
- **An agent spawned from the dashboard is visible before it has written anything.** Claude writes no transcript until a turn closes, and the agent list is built by binding each process to its session file — so a spawned agent whose opening move is a question had no file, was dropped from `GET /api/agents` entirely, and the AskUserQuestion the pty broker was already holding had no agent to hang on. The dashboard showed nothing while the terminal, which talks to the pty directly, showed the question fine; that is the whole of "the selection only works in the terminal". Resolution now falls back to the session the process names on its own command line (`--session-id` / `--resume`), producing an agent with that id, the process start as its last activity and its turn marked open. A process that names no session — an unnamed `claude`, an internal daemon — is dropped exactly as before, as is a second process claiming a session another one already took, and the fallback is Claude-only because `--session-id` is a Claude CLI flag.
- **The reply box no longer follows you into a subagent transcript.** It sat outside both branches of the agent modal, so opening a subagent swapped the transcript above it while the input below stayed bound to the parent session — anything typed there answered a session that was not on screen. The input now lives in the branch that shows the parent, and the subagent branch says why there is none: a subagent runs inside its parent's process and has no channel of its own. That branch also gained the header the session has — the subagent's kind, tokens spent and duration — so opening one shows what it cost rather than only what it said.
- **An agent whose task answers for itself is no longer stopped to ask.** The orchestrator's permission-filing path wrote a pending request for every tool call and left it for a human, with no check on the task's autonomy — unlike the HTTP path, which has auto-approved allow-all tasks since June. Only ACP-spawned stages reach that path, so a setup without an ACP spawner never saw it; with one, every tool call parked the run. `filePermissionRequest` now resolves the row for a `spec_gated` or `full` task and records a `permission_auto_approved` audit entry. The row is still written rather than skipped, because the gate polls it. Application tools (`mcp__<server>__<tool>`) keep asking: their own grant governs, not the task's autonomy. Two checks the HTTP path also makes — already-granted task permissions and permission presets — are still missing here; the orchestrator has no preset repository, and the matching helpers are unexported in the API package, so closing that gap means extracting them rather than copying them.
- **Mission control sees a task that owes a decision, not only one whose agent has already died.** The agent files its permission request in the same moment its run parks on `awaiting_user`, and its process exits a few seconds later. `blockedByPendingPermissions` — the flag the centre filtered on — requires the run to be terminal or the pid to be dead, so for those seconds the centre said "Nothing needs you" about a task that was waiting on exactly that. Measured at 3 seconds on a `manual`-autonomy task, but bounded only by how fast the process happens to exit. A new `hasPendingPermissions` ships on the wire: true whenever a non-cancelled task has unresolved requests, independent of run status. The centre filters on either flag. The task card and the overview tab still read `blockedByPendingPermissions` alone — they explain why a task is parked, which is the stranded case and remains the narrower one the orchestrator gates the next spawn on. Cancelled tasks are excluded: their leftover requests need no answer.
- **`/grant <tool>` works for the first time.** It posted to `POST /api/permission-requests/{id}/resolve`, a route the server does not register, so it answered 404 from the day it was written; its unit test asserted that same URL and stayed green. It now goes through `POST /api/permission-requests/bulk-resolve` — the route the needs-you band already uses — with the `allow_once` decision.
- **The "a new version is available" prompt is gone**, with `usePWA`. Nothing caches any more and the worker takes over on install, so no worker ever waits and the prompt could never appear. `SKIP_WAITING` stays: `refreshServiceWorker` still posts it.

- **The service worker no longer caches the app, and evicts the cache an earlier build left behind.** `precacheAndRoute` is gone and the built worker has no `fetch` handler at all, so nothing can be served from a cache any more; on activation it deletes the workbox caches and claims open pages. Push notifications, the background replay of agent messages and skip-waiting are untouched — none of them needs a cache. The precache could only ever act while the server was down, and this SPA ships inside that server, so there was no API, no stream and nothing to render; what it did instead was serve a previous build's `index.html` against a restarted server that answers **404** for the very bundle that document names, while the status bar reported the app up to date. The new worker also takes over on install rather than waiting: with nothing precached there is nothing to swap under a running session, and waiting is what would have kept the eviction from ever running — the previous worker keeps control, the new one sits in `waiting`, and the stale cache is served on indefinitely. Consequences: there is no offline start, browsers that still require a `fetch` handler will not offer to install the app, and `usePWA`'s "new version available" prompt can no longer fire, because no worker ever waits. `vite-plugin-pwa` aborts the build unless the source mentions `self.__WB_MANIFEST`, and it searches the bundled worker where a bare expression is dropped as dead code, so the token is assigned to a global that nothing reads.

- **The grant preset no longer allows anything, and no longer waits for a human to confirm it.** `POST /api/applications/{resourceId}/presets/{preset}` is replaced by `POST /api/applications/{resourceId}/denies`, which is idempotent and takes no routine. The `confirmed` and `allowForRoutine` fields, `ErrPresetUnconfirmed` and `ErrRoutineRequired` are removed. A preset that matches nothing is not an error: the application simply gets no default denies and every one of its tools asks.
- **`~/.claude.json` is no longer read to decide what a run gets.** The resolver and the tool refresh take the definition from the application row, so the error for an attached application without one now reads `application "mail" is attached but has no server definition` instead of naming that file. An application reached only through **Attach to every run** and still without a definition is skipped silently rather than failing the run. The file is still read for the one-time import, the boot reconcile, onboarding and drift detection.
- **Existing routines became `pipeline` routines and now actually run.** A one-shot migration (marker `routine-run-mode-pipeline` in `applied_migrations`) sets every routine that existed before run modes to `pipeline`; routines created afterwards default to `job`. The marker is required because the column default is `job`: after the upgrade an existing row and a newly created one are indistinguishable, so a second pass would turn new job routines into pipeline ones. The fires those routines produce changed with it — a `ready` task with `full` autonomy instead of a `backlog` task with `spec_gated`, which is what makes them run without a human.
- **The board and the pipeline columns no longer show routine jobs.** `GET /api/tasks` returns pipeline tasks unless a `kind` is asked for, and the dashboard loads `?kind=all` so a job's permission request still reaches the needs-you band while the board and the cockpit's pipeline panel filter jobs out.
- **`task_schedules.current_stage` is gone.** Nothing ever read it — a routine does not choose a stage, its run mode does — and the rename migration above no longer names it.
- **Bulk-resolving permissions for an unknown task answers 404** instead of reporting zero resolved requests.
- **Mission control and the cockpit are merged into the Zentrale.** A saved `mission` or `cockpit` view opens the Zentrale. What needs you is a queue in the page shell: docked in the Zentrale's hub, a strip above other pages, its count in the window title.
- **A round of Zentrale fixes.** A layout that fails to load offers Retry; only one that is unreadable offers Reset. The workspace re-reads the saved layout when the window regains focus, so two windows no longer silently overwrite each other. Plan reviews that need you now appear on the Dashboard. A page whose code fails to load says so, offers Reload, and keeps what needs you on screen. Spotlight hands text to the page that holds the Kontor tile, or says there is none. A decision can no longer be triggered within half a second of the next request appearing.
- **Pipeline stages renamed: `concept` is now `backlog`, `backlog` is now `ready`.** The holding pen where refinement chat runs is now called `backlog`, and the starting gun that auto-advances to implementation is now called `ready`. A one-shot data migration rewrites existing rows in `tasks.current_stage` and `stage_runs.stage` in collision-safe order (backlog→ready first, concept→backlog second). It also rewrote `task_schedules.current_stage` until that column was dropped — a routine never chose a stage, and nothing read the column. It runs exactly once, recorded in a new `applied_migrations` table, and it has to: the rename is chained, so a second pass would take the rows the first pass wrote as `backlog` and push them on to `ready` — every task parked in the refinement holding pen would start running by itself after a restart. The stored data cannot settle the question either, because a database holding no `concept` row is indistinguishable from a migrated one. `stage_runs.stage` is rewritten for all rows including terminal runs, because `GetLatestByTaskAndStage` lookups on non-terminal runs would break otherwise, and the rename is name normalization, not history falsification. The `refine.Concept` domain type, `inject_concept` tool name, and `conceptOutput`/`conceptJSON` variables are unchanged — they describe the domain object, not the pipeline stage.

### Added
- **A Kontor session in the Mission tile.** The Mission input talks to one interactive Claude session that can read and steer Kontor through the task API, with a short-lived key carrying every scope except `keys:manage`. Free text starts it as the first prompt or goes to the running session; so does a `/command` once a session runs. The tile shows the session's own terminal, its state, and **New**/**End**; `GET/POST/DELETE /api/kontor-session` and `POST /api/kontor-session/renew` serve it. "Nothing needs you" shrinks to one line so the tile gets the height.
- **A mission-control view, and it is the new entry point.** `mission` joins `ACTIVE_VIEWS` (so the command palette offers it without a second list) and puts one thing in the centre: whatever is blocking a person right now, with the reason it is first stated in words rather than as a rank. Left of it, every running task with a stage bar — how far, which stage, nothing more; the rail reports and never asks. Right of it, the existing GitHub and memory panels, which already implement the five-state contract and are now exported from `@/features/cockpit` rather than reached into.
- **The Zentrale.** One start page assembled from tiles on a twelve-column grid; *Edit layout* moves, resizes, swaps, adds and removes tiles, by pointer or keyboard; the layout is stored as the `workspace.layout` setting and validated by the server.
- **Pages of your own.** *+ New page* in the sidebar asks for a name, opens the empty page and turns on its edit mode; a page is filled like the Zentrale, and renamed or deleted (after a second, named confirmation) in its edit mode. Pages are listed under **Pages** in the sidebar and stored with the rest of the `workspace.layout` setting, so they survive a reload and a restart; the Zentrale itself cannot be renamed or deleted.
- **The Kontor tile collapses.** It shows the session's state and last output in one row; a click or `/` grows it for input, Escape collapses it.
- **The input says what it will do before you press Enter.** `readInput` settles a reading the client can carry out on its own — navigate, slash command, or capture — and the field renders it under the box. A slash command says it belongs in an agent's own prompt instead of running somewhere invisible. Readings that would need the server to interpret intent are deliberately absent: a reading shown is a promise, and one the client cannot keep is worse than none.
- **`captureTask` is one function now.** The spotlight and mission control both call `@/composables/useCapture` instead of keeping a copy of the derivation each — slug from the title, working directory from the first project's default folder. `CaptureUnavailable` separates "this system cannot capture at all" (no project, no folder — the operator's to fix) from a failed request.

- **GitHub can authenticate without a token stored in the dashboard.** `github.tokenSource` (**Settings → GitHub → Token source**) takes `setting`, the unchanged default, or `gh-cli`, which reads the token from `gh auth token` at each start. Under `gh-cli` the token field is hidden, `github.token` is never read, and the required pair reduces to `github.repos` alone — there is no half to be missing. A `gh` that is absent or logged out fails the start with gh's own advice rather than booting into calls that all answer 401, and an install that never configured GitHub never invokes `gh` at all. The command is hardcoded: no setting, request or environment value reaches its argument list. What this narrows is what is *stored*, not what an agent can *reach* — an agent with Bash is the same OS user and can run `gh` itself.

- **A pull request can be merged from the cockpit.** Each row has a **Merge** button; the first click replaces it with a confirmation naming the repository, number and title, and only that second click merges — a merge cannot be taken back, so one stray click must never perform one. The capability gate is unchanged: `github.merge` is class `spend`, so the server still refuses without an explicit grant. A refusal (HTTP 403) names both of its causes, because they are fixed in two different places — the repository allow-list under **Settings → GitHub** and a `github.merge` grant under **Settings → Grants**. A failure that came back from GitHub, such as a conflict or branch protection, is shown as-is without that hint.

- **The status bar says when the running build is older than the source it came from.** `GET /api/system/health` gained `sourceVersion` (`git describe --tags --always --dirty` in the server's working directory, cached with a 10 s TTL) and `stale`, which the server computes so the client can never disagree with it. Both fields are optional on the wire: a server that predates them renders exactly as before. An empty `sourceVersion` -- no git, no repository, a failed lookup -- is never stale, and never turns health itself into an error.
- **`POST /api/admin/restart` can rebuild before it relaunches.** An optional body `{"rebuild": true}` runs the build first; without it the endpoint behaves exactly as before. The build command is hardcoded in Go and nothing from the request reaches its command line. A failed build answers **500** with the last 40 lines of output under `output` and does **not** restart, so the old binary keeps serving. **Settings -> Server** has a **Rebuild and restart** button for it, and a failed build shows the output rather than claiming success. Until now a restart re-exec'd the same on-disk binary, so it could never pick up a merged change. The reload that follows a restart now fetches a fresh service worker and hands control to it first: the SPA is precached, so a bare reload could be served entirely from the old worker while the restarted server answered 404 for the very bundle that page asked for -- the window showing the previous build while reporting itself up to date. The refresh is bounded at 3 s and the reload happens either way.
- **The cockpit's GitHub panel shows each pull request's check state.** `GET /api/github/summary` gained a `checks` object per pull request -- `state` (`success`, `failure`, `pending`, `none`), `passed`, `failed`, `total`, `url` -- read from GitHub's check-runs API for the pull request's head commit. A check lookup that fails reads as `none` and never blanks the pull requests the repository already answered with, the same rule the surrounding repository loop follows. State is carried by text, not colour alone.
- **`Cmd+K` captures a backlog item from one line of text.** The spotlight search now returns three kinds of thing: matching tasks and agents as before, matching navigation commands (derived from `ACTIVE_VIEWS`, so a new view needs no second list), and -- when nothing matched at all -- an offer to capture what you typed as a backlog task. The slug follows the title and the working directory comes from the first project's default folder, so no project, slug or priority has to be chosen first. With no project configured it says so instead of failing silently.

- **A server's dangerous tools are denied before anyone asks.** A preset used to require a human to mark it `"confirmed": true`, and the one shipped preset never was — so its sixteen denies (sending, replying, forwarding, deleting, bulk deletion, attachment download and upload, account and spam-list changes) had never once applied. The confirmation flag is gone, and a preset now carries only denies, an optional setup block and per-account secret templates. It is **found** by what the server actually runs — its `match` string is looked for in the application's command line, longest match first — so nobody names a preset. The denies are written when an application is created, when one is imported, and again after a refresh, and on demand with `POST /api/applications/{resourceId}/denies`, which answers with the capability names it created and those already there. They are written even for a tool the last catalogue refresh did not list, because the window between adding a server and reading its tools is exactly when an unguarded tool would be reachable. `allowForRoutine`, `ErrPresetUnconfirmed` and `POST …/presets/{preset}` are gone; allows now come from answering a request once.
- **A request for a tool that is already denied is explained, not asked about.** Both payloads that carry a pending permission — the agent stream and a task's permission-request list — now say whether the capability already resolves to a deny in that run's contexts, computed with the same resolution the run's allow list is built from, so the card and the spawner can never disagree. In the needs-you band an item whose requests are all denied shows `Denied by default — change it under Settings → Grants` instead of decision buttons; a mixed item keeps its buttons, because the other requests still need an answer.
- **A server's own setup page runs inside the app.** An application whose preset declares a setup command gets a **Set up** button: the dashboard picks a free port, starts the command with `{port}` substituted and the port also exported as `SETUP_PORT`, passes the application's own environment plus its stored secrets, waits for the readiness path to answer, and shows the page in a sandboxed frame with an open-in-a-new-window fallback. One session per application — a second start replaces the first — and it ends on **Done**, after fifteen minutes idle, after thirty minutes at most, or at shutdown. The panel carries a standing notice that the setup page is reachable on the local network until it is stopped, because that is true for as long as the process runs. `POST`, `GET` and `DELETE /api/applications/{resourceId}/setup`.
- **The secret names a server needs are derived from its own accounts.** After a setup, `POST /api/applications/{resourceId}/accounts` asks the server which accounts it knows and answers with the environment variable names those accounts need — never the accounts themselves, and nothing is stored. The names are normalised exactly the way that server normalises them (upper-case, every character outside `A-Z0-9` to an underscore, verified against the published package), so what the panel offers is what the server reads. An empty account list is an empty answer rather than an error, because that is what a fresh install looks like. The panel renders one write-only password field per name, and offers manual entry when the lookup fails.
- **Every tool says whether it is denied, asks, or is allowed.** Settings → Applications showed the server's own read-only and destructive hints and stated that grants decide, without ever saying what the grants had decided. Each tool now carries the effect it resolves to with nothing but the global context, plus the contexts that carry a live allow, so a tool denied by default but allowed for one routine reads as exactly that. A revoked grant decides nothing and is not listed.
- **An MCP server is defined in the app, not in Claude's config.** Until now a run and the tool refresh read the server definition out of `~/.claude.json` at call time, so an unreadable, relocated or edited file could silently strip a running agent of its servers, and adding one meant a terminal and a restart. The definition now lives on the application row and is the only thing runs and refreshes read. **Settings → Applications → Add server** takes a name, command, arguments and non-secret environment variables and the server is available to the next run without a restart; editing replaces the fields the app knows and keeps any other key the entry carries, so a definition imported from Claude's config does not lose what the CLI wrote there. Removing a server revokes the grants on its tools, deletes its secrets, takes its mirror back out of Claude's config when it was mirrored (a server the app never mirrored stays), and leaves the registry row as `orphaned` so grants anchored to it still resolve — and is refused with `409`, naming the routines, while a routine still attaches it. Servers that existed in `~/.claude.json` when this version first started were imported once (marker `mcp-applications-entry-import`), definition and all, and marked as mirrored back into that file; the marker is required because a second pass would overwrite a definition edited in the app with the file's version. New API: `POST /api/applications`, `DELETE /api/applications/{resourceId}`, `PATCH` with `entry`.
- **A server can be mirrored into Claude's own config, and edits there are noticed.** The switch **Also available in Claude Code sessions** writes the application's definition into `~/.claude.json` as `mcpServers.<name>` so a plain `claude` session sees the same server: one key only, every other key and the file's mode kept, written through a temporary file in the same directory, and refused rather than followed when the config is a symlink. No secret value is ever written there — the exported entry is the stored definition, not the one a run gets with its secrets merged in. A failed write answers `502` and the app's state does not move ahead of the file. `GET /api/applications/drift` reports two lists: servers in that file the app does not know, and mirrored servers whose entry there no longer matches what the app wrote. Settings → Applications turns them into banners — **Found `<name>` — import?** with an Import button that has the server read the definition out of the file itself, and **Changed outside the app** with *Take the change* (stop mirroring, the edit stands) and *Write the app's version back*. Neither action sends a definition the browser invented. The dashboard watches the config directory and refreshes the panel over the existing task stream when the file changes, so no restart is needed; a config that cannot be read reports neither list, because no information is not evidence of an edit.
- **Routines run their work unattended: a routine is a job by default.** A routine had no way to run anything on its own. It fired a task into `backlog` with `spec_gated` autonomy, where the task waited for a human to approve a spec, so nothing happened; the next fire was then skipped as an overlap because that first task never reached a terminal stage. Measured on an isolated instance before this change: `run-now` produced no stage run in 45 s. A routine now carries a **run mode**. `job` — the default for new routines — fires a task of the new kind `job`: one agent run, in the routine's own working directory, with no git worktree even when `worktree.force` is set, no repository required, and no review or finalization stages around it. Its prompt is the routine's title and description, and it is finished when the agent calls `set_stage_output` with `{"summary": string, "result": string}`; `summary` says what was done, `result` carries what the routine produced. `pipeline` — what every routine that existed before this change was migrated to — fires the familiar pipeline task, but starting in `ready` rather than `backlog`. Both run with `full` autonomy, because a routine that waits for a permission prompt nobody is watching is exactly the failure this replaces; the capability gate still decides every application tool, and a run that needs a human still parks and waits (no time limit, since the previous release). A job task can never enter a pipeline stage and a pipeline task can never enter the job stage: the transition layer turns such a move into a failed run with the reason, `POST /api/tasks` answers 400 for a mismatching `stage`, and resuming a held job returns it to the job stage rather than to `implementation`. The coded model default for the job stage is the newest Sonnet (derived, never a pinned id), with the per-stage and per-spawner overrides unchanged.
- **The routine page shows what a routine actually did.** Each routine now carries its run mode as a badge, the note "Skipped N times, last …" when a fire was refused because the previous run was still in flight, and a **Runs** section listing that routine's runs newest first — status, the run's own summary, cost, start time and duration, with **Open** putting the run in the task modal. The runs come from `GET /api/schedules/{id}/runs` (at most 50, 404 for an unknown routine), which sums cost over a task's stage runs and takes status and summary from its latest one; the list refreshes itself when a task of that routine changes, so **Run now** shows the new run without a reload. Below it, **Saved decisions** lists the permissions allowed or denied for this routine, each revocable with a confirmation step.
- **Permission requests take a decision, not just yes or no.** Resolving a request — one or several at once — now accepts `allow_once`, `allow_routine`, `deny_routine` or `deny_once` (the old `outcome: granted|denied` still works and means allow-once / deny-once). `allow_routine` and `deny_routine` write a grant in the routine's context, so the answer holds for every future run of that routine without touching any other task; they are offered only for a task a routine started and only for tools of an attached MCP application, because a routine-context grant for a built-in tool would never reach a run's allow list. Anything else is refused with 400 before the request is resolved: the request stays pending and the run is not resumed. Every decision resumes the run, a refusal with a prompt naming the refused tools and, for `deny_routine`, saying the denial is permanent for this routine. In the needs-you band a routine task whose requests are all application tools offers all four decisions; every other case keeps **Approve** / **Deny** with "don't ask again".
- **Routine run modes are set in the app and over MCP.** The routine form has a **Run mode** field (Job / Pipeline task), `POST`/`PATCH /api/schedules` take `runMode`, and so does the MCP tool `manage_schedule`. A `pipeline` routine whose working directory is not a git repository is refused with "working directory is not a git repository" — on create, when the mode changes, and when the directory changes. Routines also report `skippedCount` and `lastSkippedAt`.
- **`GET /api/tasks` filters by kind and routine.** `?kind=job` lists jobs, `?kind=all` lists both kinds, `?routineId=<id>` narrows to one routine, and any other `kind` answers 400. Every task payload now carries `kind` and `routineId`.
- **Push notification when a run waits for a permission decision.** The web push service stored subscriptions but nothing sent a message, and the service worker had no `push` handler. Settings → Notifications has a **Push on this device** block: **Enable push on this device** asks the browser for permission, creates the VAPID key pair on first use and stores the subscription; the block shows whether this device is already subscribed. A permission request that stays pending then sends "Approval needed" with "<task>: <tool>" to every subscribed browser, once per pending request and never for one approved automatically — but only when **Approval Needed** is enabled with the **browser** channel ticked in the same panel — the first time a notification preference decides whether anything is sent; until now the panel only stored them. Clicking the notification focuses or opens the dashboard.
- **MCP servers registered with Claude Code can be attached to individual routines, with their secrets held by the dashboard and their tools granted one by one.** Until now every user-scope server in `~/.claude.json` reached every pipeline run: there was no way to give a mailbox to one routine and keep it away from a coding task, no place for the server's credentials except the server's own config, and no way to allow one of its tools without allowing them all, because the permission allow-list was a closed set of built-in tool names. The dashboard now mirrors user-scope servers into the resource registry at start (`kind = application`, slug `mcp-<name>`; the reserved `dashboard-channel` and `dashboard-tasks` are skipped). Servers that already existed keep reaching every run, now as an explicit, reversible **Attach to every run** flag; servers added later reach a run only when its routine attaches them — in the routine form or through `applications` on `POST`/`PATCH /api/schedules` — and the scheduler copies that list onto the tasks it creates. The task-create API deliberately does not accept `applications`: attaching a mailbox is an authority decision, and a caller able to name applications on its own task could hand itself any mailbox. Settings → Applications declares which environment variables a server needs and stores their values encrypted with the existing secret key; values are write-only over the API and reach only the attached server's `env` in the run's temporary MCP config, which a startup sweep removes once a crash has left it behind for a day. A run whose attached application lacks a required value, or whose server has left `~/.claude.json`, fails before the agent starts instead of starting without the mailbox it was given — an agent with no mailbox reports "no new mail", which reads exactly like an empty inbox. **Refresh tool list** reads the server's `tools/list` through the MCP Go client and registers each tool as a capability named exactly as Claude Code spells it (`mcp__<server>__<tool>`, class `tool`), so grants decide per tool in the run's task, routine, project and global contexts and render straight into `--allowedTools` / `--disallowedTools`; a tool without an allow grant is never allowed, allow-all autonomy included, and server-supplied read-only and destructive hints are shown but never trusted. What this does not protect against is stated in [`docs/guides/security.md`](docs/guides/security.md#application-secrets-and-mcp-applications): an agent with Bash runs as the same OS user and can read the secrets of its own run's applications. A server whose name is not a valid slug is not mirrored and therefore reaches no run at all. A shipped preset denies a known server's dangerous tools, applied automatically when the application appears (see the preset entry above, which replaced this release's earlier confirm-then-allow route). A new-mail trigger and dashboard-sent mail are not part of this change.
- **Routines are real resource-registry entries.** Every `task_schedule` now has a persistent `resources` row (`kind = "routine"`), created inline on schedule creation and reconciled at boot for existing schedules. Deleting a schedule marks its resource row as `orphaned` (not deleted), so capability grants anchored to that routine still resolve. `GET /api/resources?kind=routine` returns persisted resource rows instead of read-time projections, **narrowed to the calling user's schedules** — the `resource` table is scoped by `(scope_kind, scope_ref)`, which is global/project/path and never a person, so routines cannot be served by the generic list path without showing every user every other user's routines; identity still comes from `task_schedule.user_id`, and only the row is now persisted rather than synthesized. All four mutations sync: create, update, enable/disable (its own writer, separate from update, and the one the MCP schedule tools call), and delete. `NewTaskScheduleRepo` builds the registry repo itself rather than accepting one, because an injected `ResourceRepo` gives every call site a way to pass `nil` and lose the sync silently — which is what all three mutating call sites did, leaving the whole lifecycle dead in production while every unit test passed. Nothing substitutes it, so the parameter bought only that failure.
- **The refinement chat offers answers, not only a text box.** Refinement was a free-form chat: every reply the agent asked for had to be composed from scratch, including the ones where it had already worked out the two or three plausible answers itself. The agent now suggests up to three, and the user picks one. Mechanically this is not a new model call and not a second round trip — the turn was already being spawned and streamed, so what changed is that its output carries structure alongside the prose. It reuses the protocol `__phase_done:` established: an out-of-band block the user never sees, stripped out of the content before anything renders it. That stripping now happens in three places, once per surface the text passes through — `refine.ExtractOptions` for what gets persisted, a line-by-line state machine in `useRefinementChat.ts` for the live stream, and `OPTIONS_BLOCK_RE` in `RefinementChat.vue` as a last guard on displayed content — and each of the three names the other two, because the grammar is shared across two languages with no module that can hold it. The options ride on the turn as an optional JSON field, so a conversation recorded before this change reads back exactly as it did. Buttons appear under the **last** assistant message only and vanish the moment the user answers, whether by clicking or by typing: options belong to the question that is still open, and leaving them up invites a click that would answer a question two turns back. The free-text input never goes away — this is a shortcut, not a replacement. A block the agent opens but never closes (a cut stream, the five-minute refinement timeout) is not treated as options at all: its lines are put back into the visible answer rather than collected into a block that never arrives, because the alternative is an answer that silently truncates mid-sentence.
- **Skills the database owns now reach the disk that agent runtimes read.** `ResourceKindSkill` existed as a registry kind with no writer and no content — `GET /api/resources?kind=skill` answered `[]` and always would. A skill resource now carries content (`skill`), and a new materializer produces the `SKILL.md` files from it. The target is deliberately **not** "the filesystem": it is node × config dir × provider, so a machine running `~/.claude-personal` alongside `~/.claude` gets both, and every enabled non-Claude provider gets a *visible no-op* rather than a silent gap — none of Codex, Gemini, Junie or pi has a `SKILL.md` equivalent, and a user who authored a skill and saw nothing at all for Codex would have been misled. This is the only component in the dashboard that writes into a user's own directories, so most of it is refusal. A file it did not write is **never touched**, reported once as `foreign` and then remembered so it stops nagging. A file it wrote that a person has since edited is a `conflict`: it stops for that resource, does not merge, does not overwrite, and does not queue a retry that would overwrite it later. Ownership is proved by the recorded path, not by the marker in the file's frontmatter — a copied file carries the marker too, which is the lesson `agent-dashboard hooks install` already learned about `settings.json`. Writes are atomic (temp file, `Sync`, `Chmod`, `Rename`) and refuse any symlinked directory below the config root, while the config root itself may be a symlink because a `~/.claude` linked into `~/.claude-personal` is an ordinary dotfiles layout. Two dashboard instances on one machine cannot fight over the same files: a run takes a `coord_lock` node lease first, and the instance that does not get it degrades to read-only, reports exactly what it would have written, and names the holder — reachability is not ownership. `POST /api/skills/materialize` is the trigger and is **dry-run by default**: `{"dryRun": false}` is the opt-in to writing, and an absent field or an empty body writes nothing. It is session-authenticated, single-flighted, and takes no capability grant — the lease and the refusal rules are what gate it.
- **`skills-lock.json` is gone, together with the install command that could never work.** Nothing in the tree ever read the file — not Go, not TypeScript, not a shell script — and the documented `jq` one-liner in `docs/guides/agent-skills.md` read a `.name` key that does not exist (the name was the map key) and handed `curl` an `owner/repo` slug where it expected a URL. Its `computedHash` values were verified by nothing, and its seven entries contradicted the five the same document listed as "current skills". Provenance now lives on the registry row's `origin`/`origin_ref`, and the guide documents materialization instead. Leaving a documented command that cannot work is worse than having no command.
- **A cockpit landing view, and GitHub as the dashboard's second resource-registry Application.** The dashboard now opens on **Cockpit** rather than **Dashboard** — a glance-first grid of five panels (Agents, Pipeline, Routines, Memory, GitHub) that sits beside the existing dashboard rather than replacing it; **Dashboard** is still one click away in the **Monitor** nav group, unchanged. Each panel renders exactly one of five states — `loading`, `notAsked` (nothing configured, and the panel says why), `denied` (the server refused and named a reason), `empty` (a confirmed nothing), `failed` (the request itself errored) — or its content, never two at once: `CockpitPanel.vue` is their single owner, and every state carries its own `data-testid` (`cockpit-<panel>-<state>`) so a panel that ever collapsed a refusal into an empty list, or an unconfigured install into a healthy quiet one, would fail its own test rather than just look wrong. GitHub is the panel that reaches all five states; the Agents and Pipeline panels stream from mount and are not gated, so `notAsked`/`denied` are structurally unreachable for them, and that narrowing is recorded rather than silently assumed. GitHub itself is registered as a resource-registry **Application** (`server/internal/apps/github`, `github.Register`) with four capabilities — `github.read`, `github.search`, `github.comment` (class `reach`, the same class `obsidian.*` and `WebFetch` use), and `github.merge` (class `spend`, so `capability.defaultEffect` sends a no-grant merge straight to deny rather than to an ask a tired human could click through). Configure it from **Settings → GitHub**: `github.token` (a fine-grained PAT, `Secret: true`, encrypted the same way `obsidian.apiKey` is), `github.repos` (a comma-separated `owner/name` allow-list), and `github.baseURL` (defaults to `https://api.github.com`; override for GitHub Enterprise) — `token`/`repos` are a required pair exactly like the Obsidian trio, `baseURL` is not (it always has a default), and all three apply only after a restart. The repository allow-list (`Client.AllowsRepo`) is checked **before** the capability gate on both surfaces — `GET /api/github/summary`, `GET /api/github/search`, `POST /api/github/comment`, `POST /api/github/merge`, and the matching `github_read`/`github_search`/`github_comment`/`github_merge` MCP tools — so a capability grant can never reach a repository outside the list, and `github_search`/`GET /api/github/search` bound the query itself with an appended `repo:` qualifier per configured repository rather than filtering the response afterward. Three new MCP scopes (`github:read`, `github:write`, `github:merge`) take the tool catalogue from 47 tools / 9 scopes to **51 tools / 12 scopes**; `github:write` implies `github:read` but deliberately not `github:merge`, and `github:merge` implies `github:read` but deliberately not `github:write`, so a comment-only key cannot merge by accident and a merge-only key has no business editing discussions — see [`docs/guides/mcp.md`](docs/guides/mcp.md#scopes) and [`docs/guides/security.md`](docs/guides/security.md#githubs-token-and-repository-boundary). The client dials through the same SSRF guard the rest of the server uses (`validation.SafeDialContext`), which refuses loopback, private, link-local, and CGNAT addresses — so a GitHub Enterprise host on a LAN address (`10.x`, `192.168.x`) cannot be reached today; widening the shared guard for one application was rejected the same way it was for Obsidian, and the documented follow-up is a narrow per-client dial policy, not a change to `validation.IsBlockedIP`. **The slice's own success criterion was that a second application could run through the resource-registry/capability kernel without any kernel-specific change**, and that held at all four checkpoints: the capability declaration (`apps/github/app.go`), the REST client (`apps/github/client.go`), the four HTTP routes, and the four MCP tools each shipped with zero lines touched under `internal/capability/`, `memory.Gate`, or the capability repos — confirmed by diff, not asserted. The one shared edit across the whole slice was `server/serverapp/di.go` gaining a `GitHub` field on `ServerComponents` and a `GitHubHandler` field on `RouterDeps`, the same per-application slots that struct pair already carries for Obsidian (`Obsidian`/`ObsidianHandler`), so even that was additive wiring rather than a kernel change.
- **A routine is a thing the system has, and a grant can name it.** `capability.Decide` has ranked a `routine` context since the gate landed, the grants API and CLI accept `--scope routine:<id>`, and the Grants panel showed such a row as active — but nothing in production ever put a routine into a request's context chain, and `Decide` drops every grant whose context the request does not name. A routine grant was therefore stored, listed, and inert: it decided nothing, and there was no way to tell that from looking at it. Two things were missing, and neither was the gate. First, a task did not know which routine produced it: the link ran the other way, `task_schedule.last_task_id`, which is overwritten on every fire and so names only the most recent task. Tasks now carry `routine_id`, stamped by the scheduler's materializer with the schedule's own id. It is deliberately **not** a field of the task-create request body — a caller able to name a routine on a task it creates could hand that task another routine's permissions — so the scheduler is its only writer, and `task.metadata` (which *is* caller-supplied, and is copied verbatim from the schedule) was rejected as its home for the same reason. Second, the pipeline's automatic memory push now passes that id to `memory.Gate.Authorize` as an extra context, so `agent-dashboard grants add memory.read --pattern '*' --scope routine:<schedule id> --mode allow` decides the push for the tasks that routine fires, and outranks a project- or global-level grant, which is what the specificity order always promised. An empty `routine_id` yields no context at all rather than a blank one, because a `routine` context with an empty ref would match every grant stored with an empty `ContextRef`. **This is the memory push only.** An MCP tool call — `memory_search`, `obsidian_write`, any of them — still resolves with no routine context, because `DASHBOARD_MCP_TOKEN` is a single value taken from config and handed to every spawn (`serverapp/di_pipeline.go`), so the token an agent presents identifies no task and therefore no routine. A routine-scoped grant on `obsidian.write` remains inert; the fix for that is per-task MCP credentials, not a change to the gate. `GET /api/resources?kind=routine` also stops answering an empty list: it projects `task_schedule` rows into the registry view, narrowed to the calling user exactly as `GET /api/schedules` is. The registry table gets no routine rows and deliberately never will — a schedule already carries the trigger, the task template and the budget a routine is made of, so a mirrored identity row would be a second truth to re-sync on every create, rename, enable and delete. The projected id is the schedule's own, which is exactly the id to grant against, and an enabled and a disabled schedule report distinguishable states rather than both reading as present.
- **A memory space can be opened, not only searched.** `GET /api/memory/entries` ran an FTS query and nothing else, and `Retriever.Retrieve` returns an empty slice for an empty query text on purpose — a blank query must never dump a whole store into a spawn prompt. The panel had no other listing path and its space rows were inert text, so a space holding entries answered "No entries matched this search." unless the reader guessed a word inside one of them: a populated store and an empty one were the same screen. The route now takes an optional `spaceId` and lists that space's valid entries (`MemoryRepo.ListValid`, which already existed for the retriever) instead of searching. It authorizes `memory.read` **before** resolving the space, on the same empty value and scope the search branch checks, so an ungranted caller cannot use it to probe which space ids exist; a space whose own scope differs from the requested one answers the identical 404 a missing id does, so a grant in one scope cannot read another scope's space by id. Both branches answer the same response shape — the route keeps exactly one contract. **Settings → Memory** makes each space row a real button, shows which space is being browsed with a way back to the search, and distinguishes "this space has no entries yet" from "no entries matched this search": the two blanks mean different things and previously read as one.
- **The resource registry is readable from the dashboard.** Applications, routines, skills and memory spaces have shared one identity table since the registry landed, but the only rows anything rendered were memory spaces, reached through `/api/memory/spaces`. A new read-only route, `GET /api/resources?kind=…`(optional `scope`/`scopeRef`), answers a hand-written camelCase DTO over the existing `repo.ResourceRepo` — no schema change and no new table. It does **not** introduce a new capability, but it is not ungated either: `kind=memory_space` requires `memory.read` **in the scope the request asks for**, the same grant `/api/memory/spaces` demands for the identical rows. Without that, this route served what the gated one refuses, and the `scopeRef` echo turned it into a confirmation oracle for arbitrary filesystem paths — any extra row beyond the always-returned global ones proves that path has spaces and names them. The gate is deliberately per-kind: `application` rows are already public through `/api/plugins`, and nothing writes `routine` or `skill` yet. `kind` is **required** and is checked against an enumerated set (`application`, `routine`, `skill`, `memory_space`) rather than against the table's distinct values, so a typo is rejected as unknown even while the registry is empty; an unknown kind is a 400, and a kind nothing writes yet answers `[]` rather than 404 — "none of these exist" and "this is not a thing" are different answers. The DTO is hand-written for the same reason the memory routes' now are: encoding `*ent.Resource` directly puts snake_case on the wire and republishes every column added to the schema later, whether or not a client should see it. **Settings → Registry** renders it, with a kind picker and a scope selector, and distinguishes all five of its states — still loading, no scope ref entered yet, denied, confirmed empty, and request failed — instead of collapsing them into an empty table. Denied is a state and not an error because nothing grants `memory.read` by default, so on a fresh install a 403 on the memory spaces kind is the ordinary first thing a user sees; it names what the server actually said rather than asserting a cause, since a missing grant, a rate limit and a grant-store failure all arrive as 403. A registry that shows nothing because it was never asked looks exactly like one that holds nothing.
- **The Grants panel says whether a grant is enforced by anything.** `GET /api/capabilities` has always shipped `enforceable_by` per capability, and `agent-dashboard grants list` grew an `ENFORCEMENT` column for it, but the dashboard's own panel did not: a grant on a capability no production path resolves looked identical to one that takes effect. Each row now states which enforcement point backs it, so a grant that is stored and read by nothing is visible as such at the moment it is created rather than after it fails to do anything.
- **Each stage run now shows the memory it was actually given.** `ent.MemoryInjection` has recorded one row per memory push into a stage spawn since the memory store landed — which entries went in, the character budget, the characters spent, and how many candidates the ranker had to choose from — but the record was reachable only by `curl`, so the retrieval heuristic could be argued about and not measured. The task modal's **Stages** tab now renders it under the run it belongs to (`N entries`, `used / budget chars`, `from N candidates`), issuing one `GET /api/memory/injections?stageRun=…&stageRun=…` for the whole tab: the route grew a repeated-id form precisely so it would not be one request per run. That is a permission concern, not a performance one — `Gate.Authorize` *records* a rate-limit use on every call, so a per-run read spent one unit of `memory.read` per stage run per render, and opening a ten-run task modal against a ten-uses-per-hour grant exhausted the window. The pipeline's own memory push authorizes the same capability against the same grants, so merely looking at what memory an agent received could stop the next agent from receiving any. The single-id form is unchanged, and the id list is capped. `listInjections` authorizes `memory.read` at *global* scope unconditionally — an injection can span several spaces, so it has no single owning space to match a grant pattern against — which means a project-scoped `memory.read` grant does **not** back this call. A 403 therefore renders as one tab-level notice naming the global scope, not as the same warning repeated on every row, and a transport failure renders as a separate error: the tab shows nothing at all for a run that received no push, so "not granted", "not fetched yet" and "nothing to show" must not all arrive as the same blank.
- **The Obsidian vault integration is reachable now, not just catalogued.** `settings.Service` gained encrypted-value support: `app_setting` has new `secret`/`nonce` columns (base64 AES-256-GCM ciphertext + nonce via `internal/secretbox`), a `Definition` can be marked `Secret: true`, and a secret definition carrying a `Default` now panics at package init (`validateDefinitions`) instead of a guard that could never fire on the live write path — a secret's default would otherwise be returned in clear before anything was ever stored. `obsidian.apiKey` is the first setting to use it: encrypted on write, and masked to `********` on every read except `Service.Secret`, the one accessor that decrypts. Setting a secret to the empty string **clears** it rather than encrypting an empty value, on the HTTP surface and the CLI alike — empty means "no value", so a cleared secret reads back as unset instead of as a mask that made it look configured, and clearing is what lets the Obsidian trio return to the all-empty "vault off" state. The two surfaces have to agree: a key cleared from the CLI that still read back as `********` would show the Settings panel a filled API-key field, let its trio guard permit the save, and fail the next boot on the key it was told was there. Clearing needs no master key either — removing a secret must not depend on resolving one, least of all in the recovery command. Both the HTTP settings surface (`GET`/`PATCH /api/settings`) and the `agent-dashboard settings` CLI (`list`/`get`/`set`) now mask secrets consistently; the CLI encrypts a secret write instead of storing it plain, refuses to persist the `********` sentinel as a real value (`ErrMaskedValueRejected` — it means "leave unchanged", not "the secret is eight asterisks"), and resolves its master key lazily on the first secret write, so a read-only `list`/`get`/`grants`/`caps` invocation never generates key material as a side effect. Three more Obsidian settings joined `obsidian.apiKey`: `obsidian.baseURL`, `obsidian.vaultRoot`, and `obsidian.tlsMode` (enum `verify`/`pinned`/`insecure-loopback`, default `verify`) — **all four apply only after a server restart.** `buildObsidianClient` (`server/serverapp/di_obsidian.go`) constructs the vault client at boot from them: nothing set at all means the integration is off (logged, not an error); any one of `baseURL`/`vaultRoot`/`apiKey` set without the other two **fails the boot outright**, naming the missing settings keys — a half-configured client would otherwise come up looking healthy while every request shipped an empty `Authorization` header and failed 401. `ensureObsidianSpace` idempotently creates a global-scope `"obsidian"` memory space at boot regardless of whether the vault is configured yet, so the indexer always has somewhere to write once it is. `POST /api/obsidian/index` runs one on-demand pass of `obsidian.IndexNotes`: vault notes become `kind = "pointer"` memory entries (a sanitized first-line summary and the note's own path — never the note body). A second run while one is already in flight gets `409` rather than racing the first into permanently duplicated pointers (an `atomic.Bool` single-flight guard); an unconfigured vault gets `503`; a missing `obsidian.read`, `obsidian.search`, or `memory.write` grant gets `403` naming the capability, because this handler's `memory.Gate` is built with **no `Asker`** — nobody is watching an on-demand trigger resolve a capability question, so an `ask` decision has to deny rather than hold the HTTP response open. **A fresh install therefore denies the index run by default** until those three grants exist (`agent-dashboard grants add obsidian.read --pattern '*' --scope global --mode allow`, repeated for `obsidian.search` and `memory.write`, or the same three from **Settings → Grants**). Four new MCP tools — `obsidian_read`, `obsidian_search` (`obsidian:read` scope) and `obsidian_write`, `obsidian_delete` (`obsidian:write`, implies `obsidian:read`) — let an agent reach the vault directly, gated by the same `memory.Gate`, this time built **with** an `Asker` shared with the memory MCP tools: an agent is genuinely waiting on the tool response, so an `ask` decision may legitimately hold instead of failing closed. `RegisterObsidianTools` registers none of the four when the vault is unconfigured — an agent discovering a tool it can never use is worse than one it never sees. `obsidian_read`/`obsidian_write`/`obsidian_delete` all normalize the note path (`Client.NormalizeNotePath`) once, before the capability check, and reuse that same normalized string for both the grant check and the vault call; passing the raw path to the gate while the client separately normalized its own copy would have let `notes/../secrets/x.md` pass a `notes/*` grant and then resolve to `secrets/x.md` once it reached the client — worst on `obsidian_delete`, since a deletion cannot be undone. `obsidian_search` goes through `Client.SearchUnderRoot`, not `Client.Search`: the vault's search endpoint is vault-wide by design, so returning its results verbatim let a single `obsidian.search` grant enumerate note paths outside `VaultRoot` — filenames and existence past the boundary every other call enforces — and the surviving hits are reported root-relative, the form `obsidian_read` actually accepts. The MCP tool catalogue grows from 43 tools / 7 scopes to **47 tools / 9 scopes** (see [`docs/guides/mcp.md`](docs/guides/mcp.md#scopes)). **Settings → Obsidian** configures all four settings (base URL, vault root, a masked API key field, and a TLS-mode select) and adds an **Index now** button; saving is **blocked** while the required `baseURL`/`vaultRoot`/`apiKey` trio is only partially filled in — that is the state the server refuses to boot with, and the dashboard is what would die; all three empty stays allowed and is the working off switch (the API key field is sent empty, which clears the stored secret), and the panel turns the index endpoint's `403`/`503`/`409` into the readable messages above instead of raw status codes.
- **Grants are manageable from the dashboard, not only from the CLI.** Four session-authenticated routes — `GET /api/grants` (newest first, optional `?capability=` filter), `POST /api/grants`, `DELETE /api/grants/{id}`, and `GET /api/capabilities` for the catalogue — close half of the "no grant-management surface" gap the `agent-dashboard grants` CLI entry names. The endpoint mirrors every refusal the CLI already makes, because the reason for each is a property of the resolver rather than of the CLI: `capability.Decide` silently drops a grant whose mode or context kind it does not recognise, a `global` grant carrying a ref is unmatchable because every caller builds the global context with an empty ref, and a non-global grant with an empty ref is unmatchable because `repo.Scope.Normalize()` collapses an empty ref to `global`. A write path that accepts any of those stores a row that reads as a permission and behaves as nothing, so an unknown capability name, an invalid mode or context kind, a ref on `global`, a missing ref elsewhere, a limit count without a positive window, a non-positive expiry and a missing pattern are each refused with 400 and the valid values named. `granted_by` and `revoked_by` are taken from the request's auth payload — they exist so "who granted this" stays answerable, and an empty string would leave that permanently unanswerable. `DELETE` tombstones rather than deletes: the method describes the caller's intent, `GrantRepo.Revoke` describes the storage truth. The routes sit in the JWT group but are not admin-gated, matching `presets` (the legacy form of this data) rather than `spawners`.
- **A human's answer to a capability ask is now recorded.** `ServerEnforcer` could hold a call open for a person to allow or deny (see the entry above), but the click that turned a denial into a permission left no trace: `Asker.Resolve` handed the decision to the waiting caller and returned. `Resolve` now returns the `Pending` it resolved — the ask id is a UUID minted per ask and names nothing once the hold is released, so a caller wanting to record the decision could otherwise say only *that* something was approved, never *what*. `POST /api/capabilities/decisions/respond` writes a `capability_allow` or `capability_deny` audit event carrying the capability, the value, the context and the reason, attributed to the deciding user from the request's auth payload. The write lives in the handler rather than in `serverask`, because that is where the acting user is; putting it deeper would make `serverask` learn about authentication in order to name an actor. It is deliberately non-fatal and detached: a failed write logs and the decision still stands (it had already taken effect — a 500 would report that nothing happened when something did), and the record is written on a `context.WithoutCancel` of the request, so a browser that navigated away cannot drop the trail of a decision it already made.
- **A grants panel in Settings.** The HTTP surface added above gets its interface: **Settings → Grants** lists every grant newest-first, creates one, and revokes one. The capability name is a select fed by `GET /api/capabilities` rather than a free-text field, because a name the catalogue does not know is refused by the server and there is no reason to let it be typed. The form makes the structurally impossible unreachable — the context ref is cleared and disabled when the context is `global`, since a global grant carrying a ref is unmatchable — but it does not restate the server's rules as a second source of truth: everything else is submitted and the server's own message is surfaced verbatim on a refusal. A revoked grant stays visible and is labelled with who revoked it and when, rather than disappearing; `revoked_at`/`revoked_by` exist so that history stays readable, and hiding the row would throw away the only thing the tombstone was for. Rows carrying `granted_by = "migration:legacy"` are marked as such, so a grant the backfill inferred from a legacy `task_permissions` or `permission_presets` row is distinguishable at a glance from one a person deliberately created.
- Internal resource registry: every managed resource now has one identity row carrying kind, slug, scope, node, origin and lifecycle state. Existing plugins are reconciled into it on boot. The registry's slug rule caps plugin ids at 64 characters — a plugin manifest with a longer id is now rejected at discovery, at load, and by the plugins API. Otherwise this is the foundation the capability gate and the memory store build on.
- **Capability gate.** Permission-relevant actions are now named as capabilities (`server/internal/capability`) — a class (`tool`, `reach`, `resource`, `spend`) plus the enforcement points that may apply it — and resolved by one pure Decider that ranks the grants bound to a request's context (agent session beats task beats routine beats application beats project beats global) and, within the winning level, lets deny beat allow beat ask. Grants live in new `capabilities`, `grants`, and `grant_usages` tables: a boot-time seed catalogues every grantable Claude Code tool name, and an idempotent backfill migration turns existing `task_permissions`/`permission_presets` rows into grants (`granted_by = "migration:legacy"`) — see [`PRIVACY.md`](PRIVACY.md) for what those tables hold. The six-level ranking above describes what the Decider does when more than one context level has a matching grant; only one level is ever actually populated today, because the one enforcement path resolving real requests builds its grants directly from `task_permissions` at a single synthetic task-level context rather than reading the `grants` table — so the backfilled rows (and the project-level grants the preset backfill writes) are written and not yet read by anything in production. Of the three points a capability can declare itself enforceable at, the **spawn** point resolves decisions through the Decider in production for every task-pipeline agent: `server/internal/pipeline/spawner.go` now translates each granted `TaskPermission` into a capability grant and renders the allow-list from what the Decider returns, replacing the ad hoc filter chain that used to do the same job by hand. The in-process **server** enforcer now has a real production caller too — see the memory store entry below — which also makes the `grants` table's project/global rows readable for the first time, though still only at two of the six context levels (a memory scope's own context plus the global fallback), not the full hierarchy. The terminal-session **hook** point still runs its own, separate deny-rule matcher rather than the Decider's — see [`docs/guides/security.md`](docs/guides/security.md#capabilities-and-the-permission-gate) for exactly what each point guarantees, including the hook's deliberate fail-open timeout.
- **A human can answer a capability `ask`.** The server enforcement point (`ServerEnforcer`) now has an `Asker` wired to it (`server/internal/serverask`, built in `server/serverapp/di.go`): a decision that resolves to `ask` holds the caller's request open, surfaces as a card in the dashboard's triage band — capability, value, context and reason — and **Allow**/**Deny** there posts to `POST /api/capabilities/decisions/respond`, releasing the held call. Only the two callers with someone actually waiting may block: the HTTP memory handler (a browser request has a human on the other end) and the memory MCP tools (an agent is waiting on the tool response). The pipeline's memory push at spawn and the Obsidian vault indexer's three checks (`memory.write`, `obsidian.search`, `obsidian.read`) keep constructing a `memory.Gate` with no asker, so an ask there denies instead of stalling a spawn or a background index run — "must never ask" is a property of how the `Gate` is built, not a rule every call site has to remember. Nothing is wired under `DASHBOARD_AUTH=none`, where the respond route is not mounted either and "a human decided" would mean "any local process decided"; an `ask` there still fails closed to `ErrAskRequired`. An ask nobody answers within 25 seconds denies — this point is the complete backstop and has no fallback prompt to fall through to. `capability.Asker` now receives the `Request` alongside the `Decision`, because a `Decision` names no capability and no value, so a card built from it alone could not say what it was asking to approve. The hold-and-answer mechanism itself moved into `server/internal/askgate`, shared with the PreToolUse hook bridge, which keeps its opposite fail-**open** posture: the store only reports whether a decision arrived, never what "no decision" should mean, and each caller maps that itself.
- **`agent-dashboard grants` CLI.** Four subcommands — `add <capability>`, `list`, `revoke <id>`, `capabilities` — create, list, and revoke `grants` rows, and list the capability catalogue, closing half of the "no grant-management surface" gap noted above (an HTTP route and a settings page for the same job remain unbuilt). Like `agent-dashboard settings` and `agent-dashboard plugins`, it opens the SQLite database directly rather than going through HTTP, so it also works as a recovery path while the server is down. `add` and `capabilities` seed the capability catalogue on demand (`repo.SeedCapabilities`) before touching it, because the catalogue is otherwise only seeded at server boot, and a database the server has never opened would look empty to both commands. `add` refuses a capability name the catalogue doesn't recognise rather than writing an inert row: an unknown name has no catalogue entry, so `capability.Decide` would resolve it to a zero-value `CapabilityView` and deny forever, leaving a grant that writes successfully and then can never take effect. `revoke` tombstones (`revoked_at`/`revoked_by`) rather than deleting, so grant history survives. `GrantRepo.Create` now also rejects an invalid mode, an invalid context kind, a non-empty context ref on the `global` context, and an empty ref on any other kind, so a typo in `--scope` or `--mode` fails at write time with a listed set of valid values instead of producing a grant nothing can ever match. Only the first two mirror a rule `capability.Decide` applies when ranking — it drops a grant whose context kind or mode it does not recognise. Decide has no global-ref rule at all: it tests scope by exact struct lookup (`inScope[Context{Kind, Ref}]`), so a `{global, "x"}` grant is unmatchable only incidentally, because every caller builds the global context with an empty ref. An empty ref on a non-global kind is unmatchable for the mirror-image reason — `repo.Scope.Normalize()` collapses an empty ref to `global`, so no caller ever emits that context — and the read side (`memory.ParseScope`) already rejected it. `add` likewise refuses a `--limit-count` without a positive `--limit-window`: the window is counted backwards from the moment of the check, so a zero window finds no prior usage and the limit never triggers — a grant that reads as rate-limited and behaves as unlimited. `--expires-in` must likewise be a positive duration; a zero or negative one used to report success and create a grant that was already expired. `--pattern` is required rather than defaulting to the empty wildcard, because scope, mode, and pattern defaults compounded into the widest grant the system can express (global, allow, matches everything) from `agent-dashboard grants add Bash` alone — pass `--pattern '*'` to mean every value, which is stored literally and matches identically, since `capability.Match` routes a trailing `*` through a prefix test with an empty prefix. `revoke` refuses a grant that is already revoked, via one conditional `UPDATE ... WHERE revoked_at IS NULL` rather than a read-then-write pair, so a second call cannot overwrite who revoked it first. `add` writes the grant either way, but warns on stderr when nothing reads it: the `grants` table has exactly one production reader (`internal/memory.Authorize` through `capability.ServerEnforcer`), so any capability not enforceable at the **server** point — which is every Claude Code tool name — is stored and read by nothing until a reader exists. `list` reports that same fact per row in a new `ENFORCEMENT` column (`server` or `none`), alongside a `GRANTED-BY` column, and orders newest-first whether or not `--capability` is passed. **Specificity is resolved before mode:** the most specific context level with any matching grant decides outright, so a `project:/x` allow beats a `global` deny — a global deny is not a safety net over a narrower allow; see [`docs/guides/security.md`](docs/guides/security.md#creating-and-revoking-grants).
- **System-owned memory store.** A new local memory lets agents (and you) persist facts, preferences, and lessons that outlive one task, and pushes a budgeted, ranked extract into a stage's spawn prompt automatically. A **memory space** is not its own table — it is a row in the existing resource registry (`kind = "memory_space"`), scoped global/project/application like every other resource. Entries (`memory_entries`) carry a short `summary` (what gets pushed into a prompt) and a full `content` (pulled on demand), a `kind` (fact/preference/lesson/entity/pointer), a source, a confidence, and a validity window; writes are sanitized first — invisible/control characters are stripped, then known secret patterns are scrubbed — because a memory entry outlives the read-time scrub the rest of the app relies on; `summary` is additionally collapsed to a single line (so it can never forge the `\n\n---\n` section boundary the assembled prompt uses), while `content` keeps its original line structure — code blocks, PEM bodies, and numbered steps round-trip intact rather than being flattened. Entries are indexed with SQLite FTS5 and ranked by lexical match, scope specificity, recency, confidence, and kind — one retrieval path (`internal/memory.Retriever`) backs both the read surfaces below. Every stage spawn now retrieves up to 2,000 characters of ranked memory (a character budget, not a token count — there is no tokenizer in this codebase) and appends it to that stage's **user** prompt, never the system prompt (which is truncated head-first at 10,000 characters and would otherwise push the stage's own instructions off the end); a retrieval error, a nil injector, or a non-positive budget all degrade to no memory block rather than blocking the spawn. Access is gated by two new capabilities, `memory.read` and `memory.write` (class `resource`, enforceable only at the **server** point — memory has no spawn-time allow-list or PreToolUse hook to check against), enforced identically for the HTTP surface (`GET/POST /api/memory/spaces`, `GET/POST /api/memory/entries`, `PATCH/DELETE /api/memory/entries/{id}`, `GET /api/memory/injections`) and two new MCP tools (`memory_search`, `memory_write`, gated behind new `memory:read`/`memory:write` MCP scopes) through one shared `internal/memory.Authorize` call. **No asker is wired to the server enforcer**, so a capability decision of "ask" fails closed to a denial today rather than prompting a human — see [`docs/guides/security.md`](docs/guides/security.md#capabilities-and-the-permission-gate). There is no delete path for a memory space or a memory entry: `DELETE /api/memory/entries/{id}` marks an entry expired rather than removing it, and `PATCH .../{id}` marks one superseded — both keep the row for the audit trail. See [`PRIVACY.md`](PRIVACY.md) for what these tables hold and how (not) to remove it. **An `agent-dashboard grants` CLI now creates and revokes `grants` rows** (see the entry below) — there is still no HTTP route or settings page that does, and granting is a separate question from asking: `--mode ask` is accepted and stored, and an `Asker` is now wired to the server enforcer (see the entry above), so an ask-mode grant reaches a human instead of denying outright — except under `DASHBOARD_AUTH=none`, where no asker is built and it still fails closed. So a fresh install still denies `memory_search`/`memory_write` and every `/api/memory/*` request by default — that default has not changed — but there is now a supported, user-facing way to grant `memory.read`/`memory.write` instead of writing directly to the SQLite database.
- **Per-stage reasoning effort.** A spawner's `adapter_config` now accepts an `effort` key for adapter_type `claude` only (`server/internal/api/spawners/validation.go`); every other adapter type still rejects the key. The accepted values — `low`, `medium`, `high`, `xhigh`, `max` — are the five levels the `claude` CLI's own `--effort` flag takes, verified against `claude --help` (v2.1.248) rather than assumed; `EFFORT_OPTIONS` in `src/utils/models.ts` is a hand-kept copy of that same set for the settings dropdown, because the Vue client cannot import the Go constant — both lists say at their own definition that they must stay in parity, so a value set outside the dropdown (e.g. through the API) is still honoured, not shown as unrecognised. The control lives next to model selection in the spawner edit form: always visible, but disabled with a stated reason for the four adapter types that don't support it, so the UI can never submit a value the server would reject; a stored value outside the known five renders blank with a visible warning naming the actual value instead of silently picking a default. The resolved value reaches the spawned process — the task pipeline's native-Claude execution path reads it off the spawner it has already resolved for that stage, validates it against the known set, and renders `--effort <value>` after `--model`, dropping the flag entirely rather than forwarding anything unrecognised. `services.ResolveEffort`, added to answer "what effort is in force, and which tier of the task → project-stage → project → global-stage → default chain supplied it", has **no production caller**: the spawn path reads the already-resolved spawner directly instead of resolving a second time, so effort is now savable, editable, and honoured at spawn time, but no surface yet displays where a resolved value came from.
- **Obsidian vault as a resource-registry Application** (`server/internal/apps/obsidian`), registered at boot (`server/serverapp/di.go`) with four capabilities — `obsidian.read`, `obsidian.search`, `obsidian.write`, `obsidian.delete` — all class `reach` (vault content reaches the model, the same reasoning that puts `WebFetch` in `reach`) and enforceable only at the **server** point, since access runs through an in-process client rather than anything a spawn allow-list or a `PreToolUse` hook can see. `obsidian.write` and `obsidian.delete` are marked `Reversible: false` in the catalogue, but **nothing reads that column yet**: `capability.CapabilityView` carries only `Name`, `Class`, and `EnforceableBy`, and `capability.Decide` never references reversibility. The rule this was meant to back — a preset alone must not satisfy an irreversible capability — needs two design decisions nobody has made (extending `Decide`'s contract, and a way to tell a preset-applied grant from an explicit human one, which the grant schema cannot express today) and was **descoped**; the column is written and documented at the write site as reserved for that future decision, the same treatment `ServerEnforcer` got on the prior increment. The vault client (`obsidian.Client`) fails closed in its constructor on anything unparseable — an empty `BaseURL`/`VaultRoot`, a non-`https` scheme, an unrecognised `TLSMode` — and pins the resolved host, IP, and port at construction, so a DNS answer that changes afterwards is refused rather than re-trusted; see [`docs/guides/security.md`](docs/guides/security.md#obsidians-tls-trust-model) for the three TLS modes and what `insecure-loopback` actually restricts. `obsidian.IndexNotes` turns vault notes into memory pointers — a short first-line summary plus the note's own path, never its body — gated by the same `memory.write` capability check an agent's own write would go through, plus new `obsidian.search` and `obsidian.read` checks before, respectively, searching and reading each note, and confines every result to the client's configured `VaultRoot` before reading anything, because the upstream search endpoint is vault-wide by design. **State this plainly: that confinement is `VaultRoot`-only, not per-grant-scope** — a `memory.write` grant's scope (global/project/application) carries no vault-path semantics, so a grant narrower than the configured root does not narrow what gets indexed. **Nothing constructs this client in production today.** The settings surface meant to carry `BaseURL`, `APIKey`, `VaultRoot`, and `TLSMode` — a settings route, a settings panel, and encrypted storage for the API key — was not built on this branch; `obsidian.Register` only writes the registry identity and the four capability rows. `obsidian.IndexNotes` is the one production path that exercises `obsidian.search` and `obsidian.read` — a missing grant denies the run, the same as `memory.write` already did. `obsidian.write` and `obsidian.delete` remain untouched by any caller: nothing calls `Client.Write` or `Client.Delete` in production, and `Client.Read`/`Client.Write`/`Client.Search`/`Client.Delete` themselves still take no capability repos, so a caller that reaches the vault client directly instead of through `IndexNotes` bypasses the gate entirely. The API key that a settings surface would carry has no encrypted home either: the one plugin-agnostic key/value store, `AppSettingRepo`, persists a plain unencrypted string with no masking, and the existing AES-GCM secret path belongs to the subprocess plugin mechanism this Application deliberately does not use. **This is a security-relevant gap** — see [`PRIVACY.md`](PRIVACY.md) and [`docs/guides/security.md`](docs/guides/security.md). Even once a settings surface exists, these capabilities inherit the same gap the memory store already has above: **no `Asker` is wired to the server enforcer**, so an `ask` decision still fails closed to a denial regardless of what `agent-dashboard grants` writes. `IndexNotes`'s `obsidian.search`/`obsidian.read` checks therefore still deny by default on a fresh install, exactly like `memory.write` — the `agent-dashboard grants` CLI below can now grant them explicitly, but nothing does so by default; `obsidian.write` and `obsidian.delete` have no production caller yet for that default to apply to. **Superseded by the entry above:** the settings surface, encrypted API-key storage, the `POST /api/obsidian/index` trigger, and MCP-tool callers for `obsidian.write`/`obsidian.delete` all now exist.

  narrowing above would have been decorative: `--mcp-config` alone *adds to* the user- and
  project-scope registrations, and onboarding registers `dashboard-tasks` at user scope
  under the very same name with the broad, long-lived key (`tasks:read`, `tasks:write`,
  `pipeline:control`) — so a stage agent could simply have used that one instead. Strictness
  cuts an agent off from the servers its operator configured, so the user-scope servers from
  `~/.claude.json` are merged into the spawn's file (`server/internal/claudeconfig`, the
  reader `GET /api/onboarding/status` already used) with the dashboard's own two names
  reserved: a user-scope `dashboard-tasks` or `dashboard-channel` entry is dropped, never
  merged, which is the point of the exercise. A `~/.claude.json` that is missing, unreadable
  or malformed is logged and skipped, never fatal to a spawn. A project-scope `.mcp.json` is
  not carried over. `mcp.CallerResolver.Contexts` (`server/internal/mcp/caller.go`) resolves that key's
  `stage_run_id` through `stage_run.task_id → task.routine_id` into
  `[{task, <id>}, {routine, <id>}]` and every call to the memory MCP tools
  (`memory_search`, `memory_write`) and the four `obsidian_*` tools now passes it to
  `Gate.Authorize` as extra context, so a `--scope task:<id>` or `--scope routine:<id>`
  grant decides those calls the same way the automatic memory push already did — no other
  MCP tool goes through the capability gate today, so this is the two tool families that
  do. Every issued key gets one fixed scope set — `tasks:read`, `agent:coord`,
  `memory:read`, `memory:write`, `obsidian:read`, `obsidian:write` — six scopes, deliberately
  **not** eight. An earlier draft also included `pipeline:control` and `tasks:write`, but since
  no other MCP tool resolves through the gate, either one would have been a capability granted
  outright rather than one the gate narrows later: `pipeline:control` reaches
  `grant_permission`, `resolve_permission_request` and `approve_all_pending` on scope alone,

  `tasks:write` reaches `manage_task`'s `grant_permissions` action, letting it widen its own

  reaches a tool handler. A new hourly sweep (`mcp.SweepExpiredKeys`, started in
  `server/serverapp/serverapp.go` alongside the cost-history importer and the
  drift-detection scanner) hard-deletes expired `stage_run` rows — deleted, not
  tombstoned, since each names a stage run that already has its own record. A credential
  that fails to mint is not fatal to the spawn: the agent then runs with no task API access
  at all, since the strict config shuts the user-scope one out. **Still out of scope, deliberately:**
  interactive sessions started by hand keep using the machine-wide key and resolve with no
  task context — the `agent_session` context level still has no producer — and the
  spawner's own `--allowedTools` rendering (`SpawnEnforcer`) still builds synthetic grants
  from `task_permissions` at one fixed context and never reads the `grants` table; neither

### Changed
- The CLI folds into the single `agent-dashboard` binary — no more separate `dashboard` binary or `task build:cli` target. The CLI lived in its own main package built only by a local Taskfile target, so no release artifact ever shipped it; its subcommands include the offline lockout hatches (`agent-dashboard settings set auth.mode none`, `agent-dashboard grants add`, `agent-dashboard plugins disable`) that open SQLite directly and are meant to work while the server is down — exactly when building from source is not an option. Folding the CLI into `agent-dashboard` means every subcommand now ships in the same release artifact as the server, so a user who installed a release (not built from source) has the recovery path available too.
- `task lint` and `task fmt` now agree with the CI job they exist to predict. `task lint` reported 967 phantom `undefined` errors whenever a Go newer than `.go-version` was on `PATH`: the newer toolchain writes export data golangci-lint cannot decode (`export data version 4 is greater than maximum supported version 2`), so every package failed to typecheck. `task fmt` had the mirror-image problem — it rewrote a file CI considers correctly formatted, because `gofmt` and the formatter `task lint` actually runs disagree on trailing-comment alignment in composite literals. The two failures have different causes: formatting depends on the toolchain golangci-lint was **built** with, typechecking on the one present at **run** time. A single top-level `GOTOOLCHAIN` derived from `.go-version` covers both, rather than an `env` block per target.
- The agent modal drops its bottom drawer. Five unrelated things — tool timeline, hook events, tasks, subagents, a token table — used to share one 200px scrolling panel behind a `<details>` summary, next to a **Waterfall** tab squeezed into 300px and a **Terminal** tab. Now: session context (tasks, subagents, tools, hooks) sits beside the transcript, because it is what you read *while* reading the transcript; the transcript gets the full modal height; the token breakdown moved behind the same ⓘ affordance the agent card already uses; and the bottom is the prompt input alone.

And go-sdk 1.7.0 deprecates MCP logging (SEP-2577), which is how the dashboard delivers messages to a connected agent; the deprecation removes the feature rather than replacing it, so the call is kept and the warning suppressed at the call site until a different transport is designed. The consequence is not a duplicate write: the first target writes the file and records it under its own `target_key`, the second finds content it has no record of, because the record belongs to the other key, and `Classify` correctly calls that **foreign** — so the materializer reports a file it wrote itself as somebody else's, on every run from then on. - **The channel bridge authenticated with a global environment variable that installs need not set, so every callback answered 401.** `set_stage_output`, `request_permission` and `dashboard_reply` all post back to the dashboard using `DASHBOARD_MCP_TOKEN`, taken straight from config with no fallback. An install that never set it had the bridge posting an empty token, and the refusal was visible only inside the agent's own transcript — the dashboard saw nothing at all. The spawn's MCP config now hands the bridge the stage run's own short-lived key, the one issued per run and revoked with it. No new exposure: the same token was already in that file, in the task API server's `Authorization` header.

It received a nil interface, and its own nil-guard treated that as "auditing disabled" — silently and by design, so nothing logged and the counter stayed at zero through four measurement runs. Introduced with the event itself.

Claude Code applies `permissions.allow` from a project settings file only in a workspace that has been *trusted*, and a stage worktree is created fresh, so it never has been — the CLI discards every entry and says so: `Ignoring N permissions.allow entries from .claude/settings.json: this workspace has not been trusted`. The dashboard recorded grants, the agent received none, and the failure surfaced much later as a denied tool call. The deny list went the same way, which made the `Bash(git push:*)` block decorative in exactly the allow-all configuration that needs it. - **The `set_stage_output` MCP tool was never callable by a spawned stage agent.** A spawn runs with `--allowedTools`, and the channel allow-list named only `dashboard_reply` and `request_permission` — the bridge registered `set_stage_output` as well, but nothing permitted it. Measured on an isolated instance: 10 agent-driven stage runs completed, **zero** went through the tool. The allow-list is now derived from the bridge's tool list instead of being written out a second time, and a test reads `channel/bridge.go` directly and fails if a registered tool is missing from it.


- **A stage agent that produced text but no output envelope now gets told what was missing.** Such a run was classed `Infra: true`, the same bucket as "no session JSONL found" and "session read error", which routes to a blind requeue: the stage is retried with backoff, up to the whole auto-retry budget, and the agent is never told what went wrong — so it repeats the miss until the budget runs out and the run hard-fails. The sibling case, a schema mismatch, was already `Retryable` and gets an `IterateTransition` whose feedback quotes the error and the previous output back to the agent, escalating to the user on the second miss. The case with the *most* diagnostic information had the *least* informative recovery. Envelope misses now take the feedback path, and the message names the primary channel the agent skipped (`set_stage_output`) rather than only the fallback fence. A run that produced no text at all stays on the infra path — there is nothing to feed back. **Note for anyone comparing pipeline metrics across this change:** an envelope miss now resolves through `IterateTransition`, which marks the superseded run `done` and opens a fresh one, so these no longer accumulate as `failed` rows.
- **The new-entry form stops inviting a slug it cannot accept, and shows its error where the eye already is.** The space-slug field was free text although the valid spaces are listed two rows above it, and `createEntry` deliberately never creates a space on the fly — so a typo came back as a 403 or 404 rather than being impossible to type. The create error also rendered *below* the submit button and outside the form, which at the modal's height put it off-screen — a denied write looked like the button had done nothing at all. A parity test reads the Go struct tags and asserts the TypeScript interfaces declare exactly those keys: renaming fixtures alongside a component keeps a component suite green whatever the server actually sends, which is how this drift survived a whole wire-format sweep. It caught the missing `nodeId` on its first run.
- **The grants table has one column fewer.** `GRANTED BY` and `STATUS` answered one question between them — who put this grant here, and is it still standing — so they are now a single `Provenance` column with the actor on one line and the revocation detail beneath it. The `Active` badge is dropped rather than moved: since a revoked grant now carries a `Revoked` marker beside its mode, an active one is the row with neither, and two affirmative signals for the same fact is one more than the table can afford. A test asserts the header count, so the next column added has to be argued for rather than appended.
- **The grants table scrolls inside its own box.** Ten columns did not fit the settings dialog, and with no scroll container of its own the table pushed the whole dialog body sideways — so the columns past `ENFORCEMENT` were not merely cut off, they were reachable only by scrolling a surface nothing indicated was scrollable.
- **A revoked grant no longer reads as one that is still in force.** The Grants panel's `STATUS` column carries "Revoked <when> by <who>", but it is the last column in a table that scrolls horizontally inside the settings modal — at a 1400px viewport it is off-screen, so what a reader actually sees of a revoked row is `MODE: allow`. The only thing contradicting that was the row's `opacity-60`, which carries no meaning for assistive technology and vanishes as a signal when every visible row happens to be revoked, leaving nothing to compare against. A revoked grant now says so in text beside its own mode, where the misreading happens; the status column keeps the full detail and the row opacity stays as a secondary cue.
- **`agent-dashboard settings set` says when the value it just wrote will not reach a running server.** The settings CLI writes straight to SQLite on purpose — that is what makes `settings set auth.mode none` usable as the lockout escape hatch when the server is down or authentication is misconfigured — but `settings.Service` reads every row once at startup and nothing invalidates that snapshot from outside the process. For a key the registry marks `restart` that is exactly what the registry already promises; for one marked `live` the CLI reported success while the running server kept answering the old value, with no error anywhere. When a grant's limit was exhausted, `ServerEnforcer` downgraded the allow to an ask and a human could approve it — but that approved use was never counted. `memory.Authorize` calls `RecordIfWithinLimit` once, before any ask, and its exhausted branch inserts nothing (`grant_usage_repo.go`), so no second call ever recorded what the human let through: a limit of 3 meant "three silently, then unlimited at one click each". The adapter was built without a permission gate, and a client with no gate denied substantively — the reason class that is allowed to answer `reject_always`, so the agent remembered the refusal and stopped asking for the rest of the session. Nothing was logged, so it looked like an agent that simply would not work. - A new project's **Slug** is now derived from its **Name** as you type, instead of being an empty field you had to fill in yourself. Typing a name like `DIW-ReviewApps` and leaving the slug alone previously meant hand-writing a slug that satisfied `^[a-z0-9][a-z0-9-]{0,63}$`, and any capital letter or stray character came back from the server as a raw-regex validation error after submitting. The slug keeps tracking the name until you type your own, after which it is left alone; clearing the slug field hands it back to the name. Derived slugs are capped at the 64 characters the pattern allows, so a long name cannot generate a slug the server rejects. An existing project's slug is never rewritten when its name is edited — it is a lookup key other records already point at, so renaming it stays an explicit action. Every slug field now says so in helper text below it, and in every case spells out the accepted format. In **Settings → Projects** it distinguishes the two modes the same form renders in: for a new project, that the slug is filled in from the name and that typing into it takes it over; for an existing one, that it is a key other records point at. The compact **Create new project** panel on the task form and the task form's own **Slug** (which follows the **Title**) each say it for the one mode they have. So a name that produces no slug at all — an entirely non-Latin one, for example — no longer ends in an unexplained "Name and slug are required", nor in the server's raw pattern. The quick-create panel also stops inventing a slug at submit time: it used to fall back to one derived from the name, which sent an empty slug for a name that derives nothing and silently replaced a slug you were part-way through retyping. What it sends is now always what is on screen, and its **Slug** is marked required like **Name** and **Path**.
- `create_task` (MCP) now rejects a non-string `spawnerId` instead of ignoring it. A JSON number or boolean read as an absent value, so the task was created with the project's default spawner and the call still reported success — the requested spawner was silently dropped. The argument is now read through the same strict extractor as `projectId`/`projectSlug` and a wrong type fails the call with `spawnerId must be a string`.
- `/fork` now appears in the slash-command menu, and `/pr-comments` and `/vim` no longer do. Claude Code's built-in commands cannot be discovered — the CLI exposes no machine-readable listing — so the dashboard curates them per version, and that list had been pinned to 2.1.161 while the CLI moved to 2.1.224. It was wrong in both directions: `/fork` had been added and was missing, while `/pr-comments` and `/vim` had been removed and were still offered. The list is re-curated against 2.1.224, and the menu now surfaces the version-drift warning it already computed — previously `builtinsMayBeStale` reached the Config explorer but was discarded on the way to the command menu, so a command missing because of drift was indistinguishable from one that does not exist. The warning appears on any `/` query, including the one that matters most — a query that matches nothing at all — and is marked up as a status message (`role="status"`) so screen readers announce it instead of dropping it as a non-option child of the suggestion listbox.
- The slash-command menu now shows each command's **argument template** next to its name — `/branch-review` displays `[base-branch] [--apply-fixes]`, `/review-and-fix` its full flag list. The templates were always there in the command files' `argument-hint:` frontmatter, but the dashboard's frontmatter parser only ever read `description:`, so the field was dropped before it reached the API and the menu had nothing to render. Options were therefore only discoverable by reading the description prose, which for skills is the entire trigger paragraph. The parser now also reads `argument-hint:` (in either key order, and correctly unquoting YAML's doubled-apostrophe and backslash escapes, which real hints use), `SlashCommand`/`CommandDetail`/`SkillEntry` carry it, `GET /api/slash-commands` returns it as `argumentHint`, and the menu renders it. `GET /api/config/commands` and `GET /api/config/skills` emit the same field for API consumers; the Config explorer itself does not render it. Skills are included: each is typeable as `/<name>`, so the hint survives the skill → command conversion. Built-ins show no template — they have no file on disk to read one from. Because a command or skill file may come from an installed plugin, the hint is sanitised where that trust boundary is crossed — in the parser, so every API consumer inherits it: values that are not valid UTF-8 are dropped, C0/C1 control characters and Unicode bidi overrides are removed, and the hint is capped at 120 characters. The menu clips it again at 60 characters and carries the full value in the row's tooltip, so a long hint cannot stretch the suggestion row.
- The macOS desktop app no longer needs a **Reload** click after every rebuild. It registers no service worker: the shell serves this SPA from its own in-process server, so a precache buys no offline capability there — it only pinned the previous build's assets until the update prompt was accepted. The shell's bootstrap page marks its redirect with `?shell=desktop`, and the SPA registers a worker only when that marker is absent, so a browser visiting the same origin still registers one and keeps the PWA behaviour (offline precache and the "A new version is available" prompt). A worker installed by an earlier build is unregistered and its workbox caches deleted on launch, otherwise it would keep serving that build forever. Registrations and caches are origin-scoped, not per-host, so a browser PWA on the same origin loses its precache whenever the shell starts and re-registers on its next visit.

The shell waited for `/api/system/health` to answer 200, which a running instance does immediately — long before the new process's own server reaches its listener and reports `address already in use` — so the second window rendered the first instance's embedded SPA. A freshly built app therefore showed the previous build's frontend, which looked like a stale build rather than a port conflict. The shell now binds the dashboard address before any other startup work and keeps that listener, handing it to the server to serve on: the claim and the bind are the same act, so two launches started together cannot both get past it. The bound address is also the single source for the health poll and the webview's target URL, so a non-default `DASHBOARD_PORT` no longer sends the window to a port nothing listens on. A refused start now also says so in a dialog: an app double-clicked in Finder has no terminal attached, so the message on stderr reached nobody and the launch looked like the app doing nothing at all. - The orphan-run sweep now also reaps a `running` stage_run left behind by a crashed or killed orchestrator process — previously only non-terminal runs on a parked task, `on_hold` runs with a dead PID, and stuck `pending` runs were reaped, so a server killed mid-dispatch (before a PID was ever persisted) left a `running` row that nothing would ever pick back up. The new check only fires when the run started *before* this orchestrator process did, so a legitimately long-running async HTTP/LLM-adapter stage (which spawns no local process at all) is never mistaken for an orphan. What happens to such a run is decided by the same recovery rule the server applies at startup: a live PID is left alone, a run with a recorded session is re-queued and respawned with `--resume`, and only a run with nothing to resume from is failed.
- Token totals and costs no longer leak between unrelated sessions on Linux. The parser's incremental token-scan cache was keyed solely by inode number, and Linux filesystems (ext4, overlayfs) recycle a freed inode number almost immediately — so a newly created session file that inherited a deleted session's inode resumed that session's cached byte offset and running total, reporting a lifetime token count and cost that belonged to a session that no longer exists. macOS/APFS effectively never recycles inode numbers, which is why this only ever showed up on Linux. The cache is now keyed by path and each entry is pinned to the inode it was seeded from, so a recycled inode at a different path can never be resumed while same-path log rotation is still detected.
- Spawning an agent from inside the macOS desktop app no longer opens a second desktop window instead of starting the agent. The spawner re-executes the running binary as `<self> pty-host -- claude …` and points the MCP config at `<self> channel`; inside the desktop app `os.Executable()` is the wails binary, which parsed no arguments at all and went straight to opening a window, leaving the spawn request hanging on a PID line that never arrived. - The macOS desktop app no longer hangs when you quit it. `http.Server.Shutdown` waits for active connections but never cancels their request contexts, and every SSE handler only observes `r.Context().Done()` — so with the dashboard open its permanent streams kept the drain running into the full `shutdown.timeoutSeconds` (10 s) before it gave up with `context deadline exceeded`, and the desktop shell blocks on that drain while closing. Request contexts now derive from a context that outlives the start of shutdown by a short grace window (`RequestGraceDefault`, 2 s) before being cancelled, so an ordinary in-flight request (a DB write, a git commit, a worktree operation) still gets to finish instead of being torn out mid-mutation, while the permanent streams still release `Shutdown` well inside `shutdown.timeoutSeconds` once that grace window elapses (measured: 10.0 s down to ~0.27 s). The shell's drain wait is additionally bounded, and set above the server's own `shutdown.timeoutSeconds`, so a future handler that ignores its context cannot make the app unquittable.

### Security

- **A stage run's MCP credentials now end when its agent does, on every path that ends it.** Per-stage-run keys are revoked on the transitions that end a run (done, fail, next, both iterate branches), but three paths ended an agent without ending its run, leaving a usable key until `expires_at`:
  - **Cancelling a task** wrote the terminal stage only on the task row, so the abandoned agent's stage run stayed `running` and kept its credential. Both cancel routes — `DELETE`-style cancel on the HTTP handler and the `task_cancel` MCP control tool — funnel through `NotifyTaskTerminated`, which now ends every non-terminal stage run of the task as `cancelled`. A run that already reached its own outcome is left untouched.
  - **Requeueing a run** (rate-limit or infra retry) left its key valid, and once `sweepRequeueableRuns` promoted the run back to `pending` the respawn minted a **second** key for the same `stage_run_id` — two concurrently valid credentials, of which only the newer was ever revoked. A requeue is only ever decided from a completion result, so the agent has already exited; the run is now released at the transition.
  - **`SpawnResult.Cleanup` had no production caller.** It deletes the temp `--mcp-config` file carrying the run's bearer token, and the settings allow-list entries the spawn wrote. `stage_handlers.go` read `.PID` off the result and discarded the rest, so those files accumulated in `os.TempDir()/dashboard-<uid>/` for the life of the machine. The file is `0600` inside a `0700` per-uid directory, so this was never an exposure to other OS users — but every agent the dashboard spawns runs as that same user and can read another run's token with `Bash` or `Read`. Cleanup is now registered per stage run and runs at the same moment the credentials are revoked. This narrows the window from unbounded to the agent's own lifetime; it does not isolate concurrent agents from each other, which the same-uid process model cannot do.

  The registry is in-process: a server restart drops pending entries and leaves those files behind, where `expires_at` remains the only cap.
